02分片上传 5 步时序

100MB 文件 = 5MB × 20 分片。断了哪片重传哪片，不全重来。

sequenceDiagram
    autonumber
    participant U as 用户
    participant API as file API 1761 行
    participant SVC as file.go 1587 行
    participant FS as 文件系统
    U->>API: POST /file/upload/init / {filename, size, chunkSize: 5MB}
    API->>SVC: initUpload(req)
    SVC->>FS: 创建 /tmp/upload-{uploadID}/
    SVC-->>U: {uploadID, chunkSize: 5MB}
    loop 每个分片（并发 3-5）
        U->>API: POST /file/upload/chunk / {uploadID, index, data}
        API->>SVC: uploadChunk(req)
        SVC->>FS: 写 /tmp/upload-{uploadID}/{index}
    end
    U->>API: POST /file/upload/merge
    API->>SVC: mergeChunks(req)
    SVC->>FS: cat /tmp/upload-{uploadID}/* > /target/{filename}
    SVC->>FS: rm /tmp/upload-{uploadID}/
    SVC-->>U: {ok: true, path: "/target/filename"}
图 2：3 阶段 init → chunk → merge。断点续传友好

03文件历史快照机制

全量存（不是 diff）+ hash 去重。每次"保存文件"前自动存快照。

flowchart LR
    A[用户点保存] --> B[读当前内容]
    B --> C[算 SHA-256]
    C --> D{同 hash 存过?}
    D -->|是| E[跳过 / 不重复存]
    D -->|否| F[存快照 / file_id + hash + content]
    F --> G[更新 file_history 表]
    E --> G
    style C fill:#2f6f5e,color:#fff
    style F fill:#c97b3f,color:#fff
图 3：hash 去重 = 同内容只存一份。改 1 行 = 新 hash = 新快照

053 个必抄的设计

⭐⭐⭐⭐⭐ 必抄

1. 分片上传 / 下载

5MB × N 分片，断点续传。

必抄：Sirius Cloud L1 让用户上传大文件是必然。FastAPI 3 个 endpoint (init/chunk/merge) 30 行能写完。
⭐⭐⭐⭐ 必抄

2. 文件历史快照

防误删 / 误改。hash 去重省空间。

必抄：用户删错文件是必然事件。Web UI "文件历史" 列快照，用户点"恢复到 v3"。
⭐⭐⭐⭐ 必抄

3. 分享链接

随机 token + 过期 + 可选密码。

必抄：让用户安全分享文件给外部人。secrets.token_urlsafe(32) 生成 token。

063 个反模式（必避）

❌ 单点过大

file.go + file_history.go = 2275 行

CRUD + 编辑 + 移动 + 重命名 + 搜索 + 历史全堆一起。

避坑：拆成 file_list.go + file_upload.go + file_edit.go + file_history.go 4 个文件。
⚠️ 空间浪费

全量快照（不是 diff）

100MB 文件改 10 次 = 1GB（即使去重后改的是 1 行）。

避坑：用 git 风格 diff（每次存 vs 上次的 diff），或 zfs/btrfs snapshot（块级）。
⚠️ 散落

权限检查散落各函数

每函数自己写 if user.HasPermission，不是统一 RBAC 中间件。

避坑：FastAPI Depends / Casbin / OPA 统一权限。新加 endpoint 自动有权限检查。
