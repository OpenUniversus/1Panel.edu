🏪 一句话理解 App Store

它就像"手机应用商店 + 装修套餐样板间 + 超市补货系统"的混合体: App 表 = 商品列表, AppDetail = 不同版本, AppInstall = 你手机里已下载的应用, installWithHooks = "点击获取 → 模板渲染 → 启动容器" 的一键流程。

⚠️ 关键设计: Install 是"快速返回 + 后台跑"

你看 S2->>H: return *appInstall, nil 这一步, 它返回时其实容器还没起! 真正的 docker compose up -d 是在 go func() 里异步跑的 (L590)。前端拿到 200 之后, 还要 轮询 GET /api/v2/tasks/:id 拿真实进度。这就是为什么 taskID 字段是必填的。

🔒 互斥锁防并发

全局变量 appStoreSyncMu sync.Mutex + appStoreSyncing bool (L40-42) 保证: 同一时刻只能有一个 sync 任务在跑。第二次点"同步"会直接返 IsSyncing: true, 前端显示"同步中"。

⏱ Panic 也要解锁

L1004-1015 的 defer func() + recover() 是关键防御: 即使 sync goroutine panic 了, 锁也会释放, 且 setting.AppStoreSyncStatus 会被写成 Error。否则下一次 sync 永远卡在 "Syncing" 状态。

PageApp 是用户进入应用商店时调的第一个接口 (POST /api/v2/apps/search), 它支持 7 种筛选 + 分页 + "是否已装" 字段填充。下面这张状态图展示了每种筛选如何叠加到最终的 DBOption 链上。

🎯 7 种 DBOption 叠加

PageApp 用了 GORM 的"链式 DBOption"模式 (类似 Builder Pattern): 每个筛选条件是一个独立函数, 通过 opts = append(opts, ...) 累加, 最后传给 appRepo.Page()。这种设计的优势: 新增筛选条件只改 PageApp, 不改 Repo。

💡 软关联 (无 FK 约束)

你可能注意到: GORM 这里 没有用真正的外键约束。这是 1Panel 的一贯风格 —— app_id / app_detail_id 只是 uint 字段, 没有 References。好处: 删 App 时不会被数据库级联卡住; 坏处: 删 App 前要手动先删 Details 和 Installs (看 deleteCustomApp() 和 SyncAppListFromLocal 的事务)。

🔗 DB 联动原理 (AppDatabase DTO)

当 MySQL 装好之后, 再装 phpMyAdmin 时, 1Panel 怎么知道 "MySQL 的 IP 是多少"? 看 installWithHooks L507-514:

// 拿 "PANEL_DB_HOST" (DB 实例名) 查 databaseRepo
database, _ := databaseRepo.Get(WithByName(hostName.(string)))
// 替换成真实 docker 网络 IP + 端口
req.Params["PANEL_DB_HOST"]   = database.Address
req.Params["PANEL_DB_PORT"]   = database.Port
req.Params["DATABASE_NAME"]   = database.Name

这就是为什么 AppDatabase DTO 用 PANEL_DB_HOST 字段名, 而不是直接传 IP —— 它是"实例名", 在 install 时被解析成真实 IP。

10. 3 个生活类比

新人 onboarding 时, 下面 3 个类比能在 5 分钟内讲清 App Store 模块的整体设计。

flowchart LR subgraph S1[场景 1: 手机 App Store] S1A[App 表 = 商品列表] --> S1B[AppDetail = 不同版本 v1.0/v2.0] S1B --> S1C[AppInstall = 你已下载的应用] S1C --> S1D[Install = 点'获取'] end subgraph S2[场景 2: 超市购物] S2A[Sync = 每天补货上架] --> S2B[Detail = 商品配料表] S2B --> S2C[Install = 拿货 + 扫码 + 传送带] end subgraph S3[场景 3: 装修套餐] S3A[docker-compose.yml = 装修模板] --> S3B[Params = 业主自选 瓷砖/橱柜] S3B --> S3C[ContainerConfig = 高级定制 中央空调] S3C --> S3D[upApp = 工人进场施工] end

🏪 类比 1: 手机 App Store

把 1Panel App Store 想成"服务器版 App Store": App = 商品 (WordPress, MySQL, Redis), AppDetail = 该商品的多个版本 (WordPress 6.4 / 6.5 / 6.6), AppInstall = 你手机里"已下载的应用" (一个 App 可以装多次, 每次创建一个 install 实例)。Install() = 点"获取"按钮, SyncAppListFromRemote() = App Store 后台每天同步"今日推荐"列表。

🛒 类比 2: 超市购物

同步 (sync) = 超市每天补货上架 (从仓库拉新商品), 详情 (detail) = 商品背面的配料表 / 营养成分, 安装 (install) = 顾客拿走 + 收银台扫码 + 传送带送到停车场, 钩子 (hooks) = "买一送一"活动的赠品绑定逻辑 (Install 没传, Upgrade 传)。

🏗 类比 3: 装修套餐

docker-compose.yml = 装修模板 (水电网管预埋, 1Panel 提供), Params = 业主自选配置 (瓷砖颜色 / 橱柜品牌, 用户填表单), AppContainerConfig = 高级定制 (中央空调 / 地暖 / 网络模式), createLink() = 把水电网管接通到业主家 (写 .env / hosts), upApp() = 工人进场施工 (docker compose up -d)。
