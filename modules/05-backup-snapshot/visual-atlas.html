02容器备份机制：docker commit + save

为什么不直接备份 volume？因为跨存储驱动不兼容 + 容器配置丢。commit 把完整状态打包成 image。

sequenceDiagram

    BC->>DK: docker commit container_id snapshot_image
    DK-->>BC: image_id

053 个必抄的设计

⭐⭐⭐⭐⭐ 必抄

1. 多对象备份策略模式

每种对象一个文件，统一 BackupStrategy interface。

必抄：跟 Sirius Cloud L2 备份需求几乎 1:1。你要备份 MySQL / Redis / PG / MinIO / 网站... 每种对象一个文件。
⭐⭐⭐⭐⭐ 必抄

2. 公共 / 私有 关注点分离

backup.go 管调度 + 记录，backup_*.go 管各对象实现。

好处：提前定好"公共 vs 私有"的边界，后面系统膨胀改起来容易。
⭐⭐⭐⭐ 必抄

3. sidecar 跑备份命令

临时容器跑 mysqldump / pg_dump / mongodump，跑完即删。

Sirius Cloud 价值：你不用 Docker，但模式可以借鉴 —— 单独进程跑备份，跟 MySQL 解耦。

063 个反模式（必避）

⚠️ 单点失败

备份只落本地磁盘

/opt/1panel/backup/ 存所有备份，不接 S3/MinIO/OSS。

避坑：Sirius Cloud 备份必须存远端（你部署到真实服务器，磁盘挂了备份也没了）。设计 Storage interface（LocalStorage / S3Storage / MinIOStorage）。
⚠️ 空间浪费

没有增量备份

100GB 数据库 = 100GB 备份 × 30 天 = 3TB。即使大部分数据没变。

避坑：用 WAL 归档（MySQL binlog / Postgres WAL）做增量，或者 zfs/btrfs snapshot 块级增量。
❌ 单文件太大

backup.go 662 行

包含所有对象的"通用流程"（CRUD / 调度 / 状态机）。

避坑：拆成 backup_crud.go + backup_schedule.go + backup_status.go 3 个文件。

07Sirius Cloud 对位

Sirius Cloud 需求1Panel 对应推荐度
L2 多对象备份整套策略模式⭐⭐⭐⭐⭐
L3 跨对象系统快照snapshot_create + recover⭐⭐⭐⭐
L2 远端存储❌ 改用 S3Storage / MinIOStorage⭐⭐⭐⭐
L3 增量备份❌ 加 WAL 归档⭐⭐⭐

必抄清单

  1. 多对象策略模式（每种对象一个文件）
  2. 公共 vs 私有关注点分离（backup.go vs backup_*.go）
  3. sidecar 跑备份（解耦主进程）

抄的时候要改

  1. 加 Storage interface（支持 S3/MinIO，本地磁盘只作 fallback）
  2. 加增量备份（WAL 归档 / zfs snapshot）
  3. 加备份加密（1Panel 没加密，备份文件落盘可读）
